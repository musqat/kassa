## 확인해 보니 달랐던 것

| 예상 | 확인 결과 |
|---|---|
| 결제 정합성은 백엔드 테스트가 지키고, E2E 는 화면 연결만 본다 | 실패 경로 E2E 다섯을 쓰다 백엔드 정합성 버그 둘이 나왔다 |
| 비밀번호를 바꿔도 옛 토큰이 2시간 산다 | 같은 초에 발급된 토큰만 산다. 1.5초 띄우니 401 |
| Tomcat·Jackson·Next 의 CRITICAL·HIGH CVE 는 바로 위험하다 | 쓰지 않는 기능이었다. Jackson ReDoS 는 5만 자리 숫자에도 6~10ms |
| 가짜 게이트웨이면 어느 백엔드로 재현해도 같다 | 상태가 메모리에 있어 두 번 결과가 오염됐다 |
| 토스 문서 테스트 키로 기록 대조를 확인할 수 있다 | 같은 키를 쓰는 남의 상점 거래가 섞여 나왔다 |

## 실패 경로 E2E 가 정합성 버그를 찾았다

E2E 가 8개라 적다는 얘기에, 화면에 결과가 따로 보이는 실패 경로 다섯(응답 없음, 거절 뒤 재주문, 금액 조작, 장바구니 수량 부족·판매 종료, 비밀번호 재설정)을 더했다.
처음 생각은 "정합성은 백엔드 테스트 267개가 지키고, E2E 는 화면이 백엔드와 붙었는지만 본다" 였다.

쓰는 과정에서 둘이 나왔다.

- 응답 없음 뒤 화면에 "주문 취소" 버튼이 남아 있었다. 눌러 보니 결과를 모르는 주문이 닫혔다
- "금액 조작 → 다시 결제" 를 돌리자 2차 결제가 500 이었는데 결제는 끝나 있었다

둘 다 백엔드 테스트는 통과하고 있었다. 백엔드 테스트는 API 하나하나를 검증했고, "응답 없음 다음에 회원이 무엇을 누를 수 있나" 같은 순서는 화면을 따라가야 보였다.
고치고 나서 전체 테스트를 돌리자 세 번째(남의 주문번호로 사가가 먼저 생기는 것)가 나왔다. 자세한 건 [문제 해결](problem-solving.md).

## 옛 토큰이 살아 있다는 점검 결론이 틀렸다

라이브 보안 점검에서 비밀번호를 바꾼 뒤 옛 토큰으로 `/api/users/me` 를 부르니 200 이었다. "stateless JWT 라 만료까지 산다" 로 보고서에 적었다.

비밀번호 재설정 화면이 "기존에 로그인해 둔 기기는 모두 풀립니다" 라고 하길래 코드를 다시 봤다. 비밀번호를 바꾸면 `tokenValidAfter` 를 기록하고, 그보다 먼저 발급된 토큰을 막고 있었다.

| 로그인과 변경 사이 | 옛 토큰 |
|---|---|
| 같은 초 | 200 |
| 1.5초 | 401 |

`iat` 이 초 단위라 같은 초에 발급된 토큰은 "먼저" 가 아니다. 점검 스크립트가 로그인하자마자 바꿔서 통했던 것이다.
같은 초를 막지 않는 건 의도에 맞다. 변경 직후 같은 초에 다시 로그인해 받은 새 토큰까지 막히면 안 된다.

보고서를 고쳤고, 재설정 E2E 는 로그인 뒤 1.1초를 띄우고 재설정한다.

## CRITICAL CVE 가 이 앱에는 닿지 않았다

Trivy 로 배포 이미지를 스캔하니 Tomcat CRITICAL 3건, Jackson HIGH 5건이 나왔다. npm audit 에서는 Next CRITICAL 1건이 나왔다.
등급만 보면 급해 보였는데, 하나씩 열어 보니 이 앱이 쓰지 않는 기능이었다.

| 패키지 | 내용 | 이 앱 |
|---|---|---|
| Tomcat 11.0.24 | 서블릿 security-constraint 우회, DIGEST·FORM 인증 | Spring Security 필터와 JWT 를 쓴다. 컨테이너 인증은 없다 |
| Jackson | 숫자 문자열 정규식 ReDoS 외 넷 | ReDoS 는 숫자 5만 자리까지 보내 봤는데 6~10ms 였다. 나머지는 DataInput 파서, XML Duration, 이름 기반 다형 타입, IdentityInfo 로 이 앱이 쓰지 않는다 |
| Next 16.3.5 | `next/og` ImageResponse RCE | `next/og` 를 쓰지 않는다 |

닿는 경로는 없었지만 패치 버전만 올리면 돼서 올렸다. 부트 4.1.2 가 아직 없어 BOM 속성(`tomcat.version`, `jackson-bom.version`)으로 올렸고, 다시 스캔하니 0건이었다.
Trivy 는 CI 에 리포트로만 붙였다. 고칠 수 없는 CVE 로 PR 이 막히지 않게 하려는 것이다.

## 가짜 게이트웨이 재현이 두 번 오염됐다

"응답 없음 → 회원 취소 → 대행사에서는 승인" 을 재현하려고 가짜 게이트웨이에 승인 기록을 심고 스케줄러를 기다렸다.

첫 번째는 결과 확인이 "대행사에 승인 기록 없음" 으로 끝났다. 그사이 메모리를 재려고 같은 DB 를 보는 백엔드를 하나 더 띄웠는데, 결과 확인 스케줄러가 그쪽에서 돌았다. 그 인스턴스의 가짜 게이트웨이는 비어 있었다.

두 번째는 결과 확인까지 맞게 갔다. 그 뒤 E2E 를 돌리려고 백엔드를 재시작했고, 사가 복구가 환불을 부를 때 대행사 기록이 이미 지워져 있어 NEEDS_ATTENTION 으로 끝났다.

가짜 게이트웨이는 상태를 메모리에 둔다. 재현하는 동안은 인스턴스를 하나만 두고 재시작하지 않는다.

<br>

## 공개 테스트 키로는 대조를 확인할 수 없었다

토스 문서에 공개된 테스트 키는 가입 없이 쓸 수 있어 골랐다. 기록 대조는 대행사의 그날 거래 목록과 우리 결제를 맞춰 보는 배치라, 거래 조회 API 로 확인하려 했다.

조회해 보니 같은 키를 쓰는 다른 사람들의 거래가 섞여 나왔다. 대조 결과가 우리 코드 때문인지 남의 거래 때문인지 가를 수 없다.

대조는 가짜 게이트웨이로 확인한다. 대행사에만 있는 결제, 우리에게만 있는 결제, 금액 불일치를 직접 만들어 각각 잡히는지 본다. 실제 토스는 승인·취소·조회만 `toss` 태그 테스트로 따로 돌린다.

## 응답이 없으면 되돌리지 않는다

승인 응답이 끊기면 실패로 보고 보상(취소)하는 게 단순하다. 그러지 않고 사가를 `RUNNING` 으로 두고, 결과 확인 스케줄러가 대행사에 물어 정한 뒤 복구가 이어받게 했다.

위 재현에서 이 판단을 확인했다. 응답이 끊긴 주문에 대행사 승인 기록을 심자, 3분 뒤 결과 확인 스케줄러가 결제를 PAID 로 기록했다.
끊긴 순간 취소를 불렀다면 대행사에서 승인된 결제를 우리가 취소한 셈이다. 회원은 결제를 마쳤는데 실패 화면을 보고, 카드에는 승인과 취소가 한 번씩 남는다.

<br>

## 웹훅 본문을 믿지 않는다

웹훅은 받아서 인박스에 저장만 하고, 처리할 때 본문의 상태 대신 대행사 조회 결과로 판단한다. 토스 웹훅에는 서명이 없다.

라이브 점검에서 서명 없는 본문과 틀린 서명으로 "결제 완료" 를 보냈다. 둘 다 200 을 받고 인박스에 FAILED 로 들어갔으며, 주문은 PENDING 그대로였다.
누가 보내든 조회로 다시 확인하니 IP 필터는 붙이지 않았다. IP 목록이 바뀔 때마다 따라 고치는 수고에 비해 얻는 게 적다.

<br>

## 512MB 로 충분했다

배포를 1GB 에서 512MB 로 내리기 전에, 배포와 같은 이미지(`MaxRAMPercentage=70`)를 메모리 512MB·CPU 1개로 묶어 쟀다.

| 시점 | 메모리 |
|---|---|
| 기동 직후 | 351MB |
| 부하 중 최고 | 422MB |

부하는 15초 동안 상품 조회 3,600건과, 가입부터 결제까지 도는 회원 10명의 주문·결제 30건이었다. OOM 은 없었다.
여유는 90MB 남짓이다. 모자라면 `MaxRAMPercentage` 를 낮추거나 톰캣 스레드 수를 줄일 자리다.
