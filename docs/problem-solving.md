# 문제 해결

만들며 겪은 버그와 점검에서 드러난 빈틈이다. 각 항목은 **문제 → 추적 → 원인 → 해결** 순이다.
원인이 남아 있는 항목은 `해결` 대신 `대응`으로 적는다.

로그와 응답은 전부 실제로 재현해 받은 값이다. 예상이 빗나갔던 이야기는
[시행착오](trial-and-error.md) 에 따로 있다.

## 결제 결과를 모르는 주문을 회원이 취소할 수 있었다

<details>
<summary><b>응답 없음 뒤에도 "주문 취소" 가 열려 있었다.</b> 결과를 모르는 동안은 취소를 막는다</summary>

<br>

`문제`

승인 응답이 끊긴 주문의 상세 화면에 "주문 취소" 버튼이 그대로 있었다. 누르면 이렇게 됐다.

| 단계 | 상태 |
|---|---|
| 승인, 응답 없음 | 202, 주문 PENDING, 결제 REQUESTED, 사가 RUNNING |
| 주문 취소 | 204, 주문 CANCELED, 재고 선점 해제 |

`추적`

응답이 끊겨도 대행사 쪽에서는 승인됐을 수 있다. 가짜 게이트웨이에 그 주문의 승인 기록을 심고 상태를 지켜봤다.

```
20:23:14 order=CANCELED payment=REQUESTED saga=RUNNING
20:26:38 order=CANCELED payment=PAID      saga=RUNNING
```

3분 뒤 결과 확인 스케줄러가 대행사에 물어 결제를 PAID 로 기록했다. 회원이 취소한 주문에서 돈이 빠진 상태다.

`원인`

취소는 주문이 PAID 일 때만 대행사 취소를 부르고, PENDING 이면 주문만 닫았다.
PENDING 안에 "결제 전" 과 "승인을 걸었는데 결과를 모름" 이 섞여 있었다.

`해결`

PENDING 주문에 REQUESTED 결제가 있으면 결과를 모르는 상태로 보고 취소를 409 `ORDER_006` 으로 막는다.
결제 행은 승인을 부를 때만 REQUESTED 로 생기고 거절되면 FAILED 가 돼서 두 경우가 깔끔하게 갈린다.
주문 상세 응답에 `paymentInProgress` 를 얹어 화면은 "결제 확인 중" 을 보여 주고 버튼을 숨긴다.

대행사가 "기록 없음" 이라고 답하면 결과 확인 스케줄러가 결제를 FAILED 로 정리해 취소가 다시 열린다.
대행사 조회 자체가 계속 실패하면 결제는 REQUESTED 로 남고, 그동안 취소도 막힌다. 조회 재시도에는 상한이 없다.

</details>

## 거절된 주문을 다시 결제하면 500 인데 돈은 빠졌다

<details>
<summary><b>실패로 끝난 사가가 다시 돌았다.</b> 승인이 실패하면 주문을 닫는다</summary>

<br>

`문제`

E2E 로 "금액 조작 → 다시 결제" 를 돌리자 2차 결제에서 "서버 오류가 발생했습니다" 가 떴다. DB 를 보니 결제와 주문은 끝나 있었다.

| 시점 | 상태 |
|---|---|
| 1차: 금액 불일치로 거절 | 사가 FAILED, 결제 FAILED, 주문 PENDING |
| 2차: 승인·확정 단계 재실행 | 결제 PAID, 주문 PAID, 재고 차감 |
| 마지막 사가 완료 처리 | 예외, 응답 500 |

`추적`

```
java.lang.IllegalStateException: 완료할 수 없는 상태입니다: FAILED
	at com.kassa.saga.domain.SagaInstance.complete(SagaInstance.kt:56)
```

`원인`

오케스트레이터는 COMPLETED 사가만 막고 FAILED 사가는 그대로 다시 돌렸다.
주문 하나에 사가 하나(`order_no` 유니크)라 끝난 사가 위에서 결제가 다시 일어났다.
거절된 결제 화면에서 버튼을 한 번 더 눌러도 똑같았다.

`해결`

사가를 되살려 다시 승인하는 방법도 있었다. 멱등키는 사가 단계 행에 처음 한 번 정해지고 바뀌지 않는다. 되살리면 새 승인에 옛 키가 실리니 키와 단계 상태를 새로 정하는 규칙이 따로 필요하고, 그 규칙이 틀리면 한 주문에 결제가 두 번 붙는다.

승인이 실패해 보상까지 끝나면 주문을 FAILED 로 닫고 선점을 푼다. FAILED·NEEDS_ATTENTION 사가에 승인이 다시 오면 409 `PAY_004` 다.
장바구니는 확정 단계에서만 비우니 거절된 주문의 상품은 장바구니에 남아 있고, 거기서 다시 주문한다.

</details>

## 가입만으로 메일을 무제한 보낼 수 있었다

<details>
<summary><b>재전송에는 제한이 있었지만 가입에는 없었다.</b> IP 마다 10분에 5번</summary>

<br>

`문제`

라이브 보안 점검에서 없는 주소로 가입 15건을 4.2초에 보냈더니 인증 메일 15통이 나갔다.
배포는 Gmail SMTP 라 하루 발송 한도를 다 쓰거나 스팸 신고로 계정이 막히면 진짜 회원의 인증 메일도 안 나간다.

`원인`

인증 메일 재전송과 비밀번호 재설정은 같은 주소에 1분·시간당 제한이 있었다. 가입마다 나가는 메일에는 아무 제한이 없었다.

`해결`

IP 마다 최근 10분 가입 시각을 들고 5번을 넘으면 429 `COMMON_002` 를 준다. 머신이 한 대라 메모리에 두고, 같은 IP 는 `compute` 로 한 번에 하나씩 센다.
제한값을 5로 띄운 서버에 두 스크립트가 동시에 가입을 보냈을 때 받은 건 합쳐서 5건이었다.

</details>

## 배포 백엔드가 켜지기 전에 다시 멈췄다

<details>
<summary><b>스프링 기동이 Fly 프록시가 기다리는 시간보다 길었다.</b> 끄지 않고 일시 정지하게 했다. 배포 직후 콜드 부팅은 여전히 길다</summary>

<br>

`문제`

처음에는 Fly.io 체험 계정이라 머신이 5분마다 멈췄다. 카드를 등록하고 요청이 없을 때만 멈추게(`auto_stop_machines = "stop"`, 최소 머신 0) 바꿨는데,
일주일 뒤 백엔드가 아예 응답하지 않았다. 모든 요청이 36초 부근에서 503 이었고, Vercel 화면은 실패 화면으로 끝났다.

`추적`

머신 이벤트를 보니 기동 중에 프록시가 머신을 멈추고 있었다.

```
stopping  stop   proxy  07:38:34
stopped   crash  flyd   07:38:45  exit_code=-1, requested_stop=true
starting  start  proxy  07:38:54
```

같은 시간대 앱 로그에서 스프링 컨텍스트 초기화에만 120초가 걸렸고, 4분이 지나도 기동이 끝나지 않았다.
로컬에서 CPU 1개·512MB 로 같은 이미지를 띄우면 15초였다(한 번 잰 값).

`원인`

요청이 오면 프록시가 머신을 켜고 36초쯤 기다리다 503 을 준다. 처리된 요청이 없으니 머신은 유휴로 보이고, 기동이 끝나기 전에 다시 멈춘다.
다음 요청에 처음부터 다시 기동하니 끝까지 뜨지 못했다. 기동이 지난주(31초, 107초)보다 크게 느려진 건 공유 CPU 의 여유분을 반복 기동으로 다 쓴 탓으로 본다. 추정이다.

`대응`

멈출 때 끄지 않고 메모리째 일시 정지하게(`auto_stop_machines = "suspend"`) 바꿨다.
일시 정지한 머신은 다시 기동하지 않고 그 상태에서 재개하고, 멈춘 동안 요금은 끈 머신과 같다([Fly 문서](https://docs.fly.io/reference/suspend-resume)).

일시 정지 뒤 처음 재 보니 머신은 0.88초 만에 재개했지만, DB 를 쓰는 첫 요청이 30초 뒤 500 이었다.

```
HikariPool-1 - Connection is not available, request timed out after 30065ms (total=9, active=1, idle=7, waiting=0)
```

놀던 연결 7개가 일시 정지 동안 끊겼는데, 재개한 앱은 살아 있다고 여겼다. 빌려줄 때 연결마다 검사를 기다리다(기본 5초) 30초 제한을 넘긴 것으로 본다.
쉬는 동안 남기는 연결을 2개로 줄이고(`minimum-idle`), 그 밖의 연결은 2분 뒤 닫고(`idle-timeout`), 검사 대기를 1초로 줄였다(`validation-timeout`).

| 측정(한 번씩 잰 값) | 고치기 전 | 고친 뒤 |
|---|---|---|
| 일시 정지 20~30초 뒤 헬스 체크 | 200, 0.88초 | 200, 0.73초 |
| 일시 정지 20~30초 뒤 첫 DB 요청 | 500, 30.5초 | 200, 0.70초 |
| 일시 정지 20분 뒤 첫 DB 요청 | - | 200, 3.1초 |

배포 직후나 호스트 이전 뒤처럼 스냅숏이 없으면 콜드 부팅한다. 배포 직후 콜드 부팅은 첫 응답까지 42초(스프링 기동 29.5초)였다.
공유 CPU 에서 기동이 길어지는 원인은 그대로다.

</details>
